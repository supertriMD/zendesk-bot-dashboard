# Part 1 — Zendesk Bot Performance Dashboard
## Claude Code Build Brief

*A self-contained build. Delivers a Streamlit dashboard showing (1) estimated % of questions answered to satisfaction, split by email vs website, and (2) the top-5 themes the bot could not answer. Standalone — needs none of the CMS (Part 2).*

---

## 0. What you're building (one paragraph)

A scheduled job pulls Zendesk conversations (email tickets + web/messaging) into a local store, Claude scores each conversation as resolved / partial / unresolved and tags its topic, and a Streamlit app visualises the resolution rate over time and the ranked list of unanswered themes. The "top-5 unanswered" is the actionable output — it's the content backlog that later feeds the CMS.

---

## 1. Guardrails to state up front (paste into Claude Code first)

> Context for the whole build:
> - This is an analytics/reporting tool. Read-only against Zendesk — it must never modify, reply to, or close tickets.
> - The "satisfaction %" is an ESTIMATE from an LLM judge, not ground truth. Label it as such everywhere in the UI ("estimated resolution rate"). Never present it as precise.
> - All secrets (Zendesk token, Anthropic key) come from environment variables / a .env file that is gitignored. Never hardcode credentials. Never print them.
> - Batch/scheduled design, not real-time. Jobs should be safely re-runnable (idempotent) — re-running must not double-count.
> - Store raw conversations separately from scored results, so we can re-score without re-pulling.

---

## 2. Architecture

```
Zendesk API ──(pull job)──▶ raw store (conversations)
                                   │
                          (scoring job: Claude)
                                   │
                                   ▼
                          scored store (labels + themes)
                                   │
                                   ▼
                          Streamlit dashboard
```

**Storage decision (keep it simple to start):** local **DuckDB** file (you already use DuckDB as a proving layer). No cloud DB needed for v1. If/when volume grows or you want it shared, the same schema lifts into **BigQuery** (your analytics cloud) with minimal change — write the data-access layer behind one module so the swap is one file.

## 4. Data schema (schema.sql)

```sql
-- Raw conversations (pulled from Zendesk, never overwritten)
CREATE TABLE IF NOT EXISTS conversations (
    conversation_id   VARCHAR PRIMARY KEY,   -- Zendesk ticket/conversation id
    channel           VARCHAR,               -- 'email' | 'web' | 'messaging'
    created_at        TIMESTAMP,
    updated_at        TIMESTAMP,
    subject           VARCHAR,
    full_text         VARCHAR,               -- concatenated turns, role-labelled
    turn_count        INTEGER,
    ended_with_human  BOOLEAN,               -- escalated/handed to agent
    user_rating       VARCHAR,               -- 'good' | 'bad' | null (widget CSAT)
    pulled_at         TIMESTAMP
);

-- Scored results (regenerated by re-running the scorer; keyed to conversation)
CREATE TABLE IF NOT EXISTS scores (
    conversation_id   VARCHAR PRIMARY KEY,
    resolution        VARCHAR,   -- 'resolved' | 'partial' | 'unresolved'
    confidence        DOUBLE,    -- judge's self-reported 0-1
    primary_topic     VARCHAR,   -- short tag, e.g. 'parking', 'transfers'
    unanswered_reason VARCHAR,   -- if not resolved: why, in one line
    scored_at         TIMESTAMP,
    model             VARCHAR
);

-- Theme rollup (optional cache; can also compute live)
CREATE TABLE IF NOT EXISTS themes (
    theme             VARCHAR,
    example_question  VARCHAR,
    count             INTEGER,
    period            VARCHAR
);
```

## 5. The build prompts (run in order in Claude Code)

### Prompt 1 — scaffold
> Create the project structure above. Write requirements.txt (streamlit, duckdb, anthropic, requests, python-dotenv, pandas). Write .env.example with ZENDESK_SUBDOMAIN, ZENDESK_EMAIL, ZENDESK_API_TOKEN, ANTHROPIC_API_KEY. Write .gitignore (.env, *.duckdb, __pycache__). Write db.py exposing get_connection(), init_db() that runs schema.sql, and helper upsert functions. Keep all DB access in db.py so the store can later be swapped to BigQuery.

### Prompt 2 — pull job
> Write pull_conversations.py. Use the Zendesk API to fetch tickets AND messaging/web conversations updated since the last pull (incremental — track a high-water mark). For each, assemble full_text as role-labelled turns ("User:" / "Bot:" / "Agent:"), detect channel, set ended_with_human if an agent joined, capture user_rating (satisfaction) if present. Upsert into conversations. Read-only against Zendesk. Handle pagination and rate limits (back off on 429). Make re-runs idempotent.

### Prompt 3 — the LLM judge (the important one)
> Write score_conversations.py. For each conversation not yet scored, send the full_text to Claude with this rubric: classify resolution as 'resolved' (the user's question was fully answered and they showed no further confusion), 'partial' (answered but left a gap or a follow-up the bot couldn't take), or 'unresolved' (the bot deflected, said it didn't know, gave a wrong-topic answer, or the user expressed dissatisfaction). Also return: a short primary_topic tag (lowercase, 1-2 words), a one-line unanswered_reason if not resolved, and a confidence 0-1. Return strict JSON only. Write results to scores. Batch politely, handle malformed JSON defensively, make it idempotent (skip already-scored unless --rescore passed).

### Prompt 4 — themes
> Write themes.py. Take all 'unresolved' + 'partial' conversations in a period, and cluster their primary_topic + unanswered_reason into coherent themes using Claude (e.g. merge 'parking', 'car park', 'where park' → "Parking & access"). Output the top 5 themes with a count and one representative example question each. This is the content backlog.

### Prompt 5 — dashboard
> Write app.py (Streamlit). Show: (1) headline "Estimated Resolution Rate" as a % with a clear 'estimated' label and a tooltip explaining it's an LLM judgement calibrated against human review; (2) that rate as a trend line over time; (3) the same split by channel (email vs web) side by side; (4) a "Top 5 things the bot couldn't answer" panel with theme, count, example; (5) a date-range filter and a raw-conversation drill-down for any theme. Read only from the scored store via db.py. Keep the design clean; put the estimate caveat visibly near the headline number.

### Prompt 6 — calibration (do not skip)
> Write calibration/sample_for_review.py to export 50 random scored conversations to a CSV with a blank human_label column. Write calibration/compare.py to read the filled-in CSV back and report agreement % between human labels and Claude's labels, plus a confusion breakdown. This tells us how far to trust the resolution number before we quote it to anyone.

---

## 6. Sequence & acceptance

1. Prompts 1–2 → confirm real conversations land in DuckDB, both channels. **Acceptance:** row counts match a Zendesk spot-check.
2. Prompt 3 → score a small batch, eyeball 10 by hand. **Acceptance:** labels look sane.
3. Prompt 6 → run calibration on 50. **Acceptance:** you know the agreement % (aim >80% before trusting the headline; below that, tune the rubric).
4. Prompts 4–5 → dashboard live. **Acceptance:** top-5 themes match your gut sense of what users struggle with.

---

## 7. What this deliberately does NOT do (scope guard)

- No writing back to Zendesk. Read-only.
- No real-time. Scheduled pulls (start manual, add cron later).
- No CMS integration yet. The top-5 output is a list you act on manually for now; wiring it into the CMS backlog is a Part-2 step.
- No cloud infra required for v1 (local DuckDB). BigQuery is a later swap, isolated to db.py.

---

## 8. First thing to check before building
- **Zendesk API tier / rate limits** on your plan — decides pull cadence and whether full history is feasible in one go.
- **Whether the web-widget conversations are exposed via the API** the same way tickets are — confirm both channels are reachable, since "email vs web split" is a core requirement.
